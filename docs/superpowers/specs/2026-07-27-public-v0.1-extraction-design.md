# Team Memory Agent Public v0.1 Extraction Design

## Problem

Teams need a trustworthy record of work that is scattered across source-control
forges, shared chat channels, and member-owned local tools. Operators need useful
team and project reports, while members need to know exactly what leaves their
machines. The existing private implementation proves the ledger, collectors,
synthesis, and vault-rendering model, but it includes company-specific operating
assumptions and has no completed importer for member-reviewed bundles.

Public v0.1 must turn that implementation into a reusable local-first product
without changing the live private deployment.

## Product Definition

`team-memory-agent` is one open-source product with two separately installable
Python packages:

- `teammem` is the operator-facing hub application. It collects central signals,
  stores attributed events in a local SQLite ledger, imports member-reviewed
  bundles, and renders disposable Markdown projections.
- `teammem-memberkit` is the member-facing client package. Its command remains
  `memberkit`; members install it without cloning or installing the hub. It also
  owns the opt-in local schedule that prepares drafts and reminds members to review.

`teammem-bundle/v1` is the versioned wire protocol between them. It is not an SDK
or a third product. "Collective Cognition" may describe the product philosophy,
but "collective-memory" is not a repository, package, or runtime component.

The public repository is a monorepo so protocol changes can be tested against
both producer and consumer. Package installation remains independent.

The public repository will contain:

that plugin install or invoke the public `teammem-memberkit` package.

## Production Isolation

The existing live private checkout is a read-only source for extraction. Public
work must not:

- edit or run its daily script;
- edit or reload its launchd job;
- read from or write to its live ledger during tests;
- use its live company vault as an output;
- change files in the private company SDK;
- change private configuration or credentials;
- create a second scheduled collector.

Tests use only temporary directories, fixture configuration, fixture bundles, and
temporary SQLite databases. Public extraction does not authorize a commit, push,
package publication, or production migration.

## Extraction Strategy

Public v0.1 uses a clean initial import rather than publishing private repository
history. Only reusable tracked source, tests, and example configuration are copied.
Private planning history and operational documentation are rewritten as concise
public documentation.

The extraction must remove or generalize:

- company and employee names;
- internal hostnames, IP addresses, group IDs, repository paths, and certificates;
- personal and company-vault filesystem paths;
- private deployment topology;
- company-specific project fixtures;
- package descriptions and help text naming the originating company;
- fixed model selections presented as product policy.

GitLab and Feishu remain supported adapters. Claude CLI and Anthropic API support
may remain optional synthesis backends, but documentation and configuration must
make the core ledger, importer, and deterministic rendering usable without them.

## Bundle Protocol

`schemas/teammem-bundle-v1.md` becomes the canonical source of
`teammem-bundle/v1`. Version 1 remains frozen:

- bundle paths are `<member>/bundle-<member>-<YYYY-MM-DD>.json`;
- the JSON `member`, directory member, and filename member must match;
- `events` is authoritative and `journal_md` is derived;
- an empty event list is valid;
- the hub assigns `person`, `source`, and the event deduplication hash;
- event order is not semantically significant;
- a repeated unchanged bundle inserts no duplicate ledger rows;
- changed content is inserted as new evidence rather than updating prior rows;
- timestamps without offsets are treated as member-local time.

MemberKit can continue using a local claude-mem database as its first source
adapter. The public interface must describe that dependency plainly. Adding more
local sources is outside v0.1.

## Importer

The hub adds an `import-bundles` command with explicit paths:

```text
teammem import-bundles \
  --inbox <directory> \
  --archive <directory> \
  --quarantine <directory> \
  [--dry-run]
```

Processing is deterministic:

1. Discover `*/*.json` bundle files in lexical order.
2. Read UTF-8 JSON without following symlinks.
3. Validate the relative path, filename, schema, top-level fields, member slug,
   date, and every event.
4. Resolve the member slug through the hub roster.
5. Convert all events before starting a database write.
6. Insert the converted events in one transaction using the existing
   `(person, source, hash)` uniqueness rule.
7. Write an accepted bundle to a temporary archive file, sync it, atomically place
   the content-addressed revision, then remove it from the inbox.
8. Move a rejected bundle to quarantine with a machine-readable reason file.
9. Print a summary containing accepted, quarantined, discovered-event, and
   newly-inserted-event counts.

Validation failures never partially insert a bundle. Filesystem failures after a
successful insert are reported as errors; a retry is safe because ledger insertion
is idempotent and a partial archive revision is atomically replaced with verified
input bytes. Accepted revisions are archived at
`<member>/<bundle-filename>/<bundle-sha256>.json`. An identical revision is treated
as already processed. A different revision of the same member/date bundle receives
its own content-addressed archive path; its previously imported events deduplicate
and only changed or newly added events are inserted.

Dry-run performs discovery, parsing, validation, identity resolution, and event
conversion, but does not create a database, move files, or write reason files.

### Event conversion

Each accepted member event becomes a hub event:

- `person`: canonical roster slug resolved from the bundle member;
- `source`: `bundle:<member>`;
- `ts`, `kind`, `summary`, `project`, and `refs`: validated bundle values;
- `raw`: canonical JSON for the individual bundle event;
- `hash`: SHA-256 over canonical JSON containing the protocol schema, member,
  date, and individual event.

Including the bundle date prevents indistinguishable local-time events from two
different bundle days from collapsing. Excluding `journal_md` ensures derived prose
cannot change authoritative event identity.

## MemberKit Distribution

The package distribution name is `teammem-memberkit`; the executable remains
`memberkit`. A member's normal workflow is:

```text
pipx install teammem-memberkit
memberkit draft
memberkit review
memberkit push
```

Only contributors clone the repository. MemberKit defaults move from
the company-specific configuration directory to
`~/.config/teammem/memberkit.env`. Configuration remains overridable with
`MEMBERKIT_*` environment variables.

Git remains the v0.1 inbox transport because it already provides reviewable,
auditable delivery. Other transports are outside v0.1; the hub importer depends
only on a local inbox directory.

## MemberKit Schedule and Catch-up

Package installation does not silently modify the operating system. The required
one-time onboarding command configures MemberKit and installs an opt-in schedule:

```text
pipx install teammem-memberkit
memberkit setup
```

`memberkit setup` proposes 17:30 in the member's detected local timezone. Pressing
Enter accepts it; the member can choose another `HH:MM` value or decline scheduling.
The same behavior is available non-interactively:

```text
memberkit schedule install [--time HH:MM]
memberkit schedule status
memberkit schedule remove
```

The initial public implementation supports macOS launchd. Other platforms can call
the portable `memberkit scheduled-run` command from their native scheduler, and the
documentation provides the command without claiming automatic installation support.

A scheduled run:

1. Reads the configured local source without modifying it.
2. Refreshes unfinished drafts without overwriting member edits.
3. Finds previously unseen events for yesterday and today using event fingerprints.
4. Adds late events to a catch-up draft for their original local calendar date.
5. Creates or updates local draft files only.
6. Leaves malformed or partially edited existing drafts untouched.
7. Shows a local desktop reminder listing every date that still needs review,
   including pending dates older than yesterday.
8. Never imports push code, pushes, commits to the inbox, or transmits data.

Calendar attribution follows the event's member-local timestamp, not the run date.
For a 17:30 Monday run, Monday events through 17:30 enter Monday's draft. Events from
17:30 through 23:59 are discovered on Tuesday but remain in a Monday catch-up draft.
Events at or after 00:00 local belong to Tuesday.

MemberKit stores local event fingerprints and one of three states:

- `pending`: present in a local draft and not yet pushed;
- `approved`: included in a reviewed bundle that was pushed;
- `excluded`: removed by the member before push.

Before refreshing an existing draft, MemberKit compares it with its recorded pending
events. Missing pending events become `excluded`; newly discovered events are added
without restoring excluded events. On push, included pending events become
`approved`. Approved and excluded events do not appear in later drafts unless the
member explicitly resets local state. This preserves redaction across catch-up runs.

Multiple dates may remain pending. `memberkit review --date YYYY-MM-DD` and
`memberkit push --date YYYY-MM-DD` operate on one date at a time. Reminders repeat on
later scheduled runs until every pending date is reviewed or explicitly dismissed.
Dismissal marks that date's pending events excluded; it does not transmit them.

## Privacy and Security

The public documentation must make these product guarantees explicit:

- MemberKit reads its configured local source in read-only mode.
- A member can review and edit the authoritative event list before pushing.
- Scheduled runs create local drafts and reminders but never push.
- Member redactions persist across scheduled catch-up runs.
- Raw local databases, direct messages, and local files are never included.
- Shared-channel collection requires a visibly present integration.
- The hub does not score, rank, or evaluate employee performance.
- Ledger and rendered output stay local unless the operator separately configures
  a repository push.

The repository must ignore databases, generated vaults, environment files,
credentials, certificates, MemberKit work directories, archives, quarantines, and
Python build/test artifacts. A release scan must reject internal addresses, known
private paths, and credential-like assignments. The extracting operator supplies
origin-specific organization and roster identifiers through an uncommitted private
deny regular expression so the public scanner does not itself disclose them.

## Error Handling

- Configuration errors return exit status 2 with the missing setting named.
- Malformed or semantically invalid bundles are quarantined individually and do
  not prevent other bundles from being processed.
- Unresolvable member slugs are quarantined; MemberKit bundles never create
  `_unmapped` people.
- Database or filesystem failures return exit status 1 and retain enough state for
  a safe retry.
- Collector network failures retain their existing explicit error behavior.
- Optional synthesis unavailability does not prevent collection, import, ledger
  queries, or deterministic rendering.

## Testing

Tests must use Python 3.11 or newer and must not require network access,
credentials, a real inbox repository, claude-mem, or an LLM.

Required importer coverage:

- valid bundle conversion and insertion;
- identical re-import inserts zero rows;
- changed event content inserts a new row;
- empty event list archives successfully;
- schema, path/member, filename/date, field-type, event-field, and identity
  mismatches quarantine without database writes;
- a multi-event bundle is all-or-nothing;
- accepted archive placement and reason-file placement;
- identical archive collision is safe;
- an interrupted partial archive revision is atomically repaired on retry;
- different content for the same member/date creates a separate archive revision;
- dry-run performs no writes;
- symlinks are rejected;
- non-ASCII input is preserved;
- member-local timestamps are accepted.

Required scheduling coverage:

- schedule installation defaults to 17:30 local time;
- scheduled runs never invoke push or Git;
- events after the reminder but before midnight remain on the original date;
- events at or after local midnight enter the next date;
- late events appear in a catch-up draft;
- an edited pending draft is refreshed without restoring removed events;
- approved and excluded fingerprints do not reappear;
- multiple pending dates remain independently reviewable;
- older pending dates remain in later reminders;
- invalid member-edited drafts remain byte-for-byte untouched;
- importing the scheduled CLI path does not import the push module;
- setup explicitly offers accept, change, or decline for the default reminder;
- schedule status and removal are idempotent;
- scheduler tests use a temporary launch-agent directory and never modify the
  developer's real scheduler.

An integration test must generate a bundle with the public MemberKit code, import it
with the public hub, re-import it, query the ledger, and render a temporary vault.

Existing reusable hub and MemberKit tests are retained only after their fixtures and
assertions are sanitized. CI installs and tests the hub and MemberKit independently,
then runs the integration test.

## Public Documentation

The README leads with the user problem and the complete privacy-preserving flow. It
must distinguish the hub, MemberKit, protocol, and optional adapters. Quick starts
use local fixtures and temporary paths, not company infrastructure.

Architecture documentation explains ledger-as-truth and regenerated projections.
Privacy documentation states collected and excluded data. Deployment documentation
offers manual invocation first; launchd is an optional macOS example, not the
product's required runtime.

Apache-2.0 is the proposed license because it is permissive and includes an explicit
patent grant. Adding it locally is not permission to publish: public release remains
gated on confirmation that the code owner authorizes that license.

## Success Criteria

Public v0.1 is ready for publication review when:

1. A fresh environment can install the hub and MemberKit independently.
2. A member can produce, review, and push a v1 bundle without cloning this
   repository.
3. An opted-in default schedule drafts locally at 17:30, catches up late events on
   their original date, preserves redactions, and never pushes automatically.
4. The fixture inbox flows through validation, ledger insertion, archive, and
   Markdown rendering.
5. Re-importing the same bundle inserts zero new events.
6. Invalid bundles never produce partial ledger writes.
7. The full test suite passes without network access or private configuration.
8. The sanitized repository scan finds no private identities, infrastructure,
   credentials, or live paths.
9. The live private checkout's status, tracked-file hashes, scheduler definition,
   database metadata, and vault target are unchanged by the extraction.
10. No commit, push, package publication, private-SDK change, or production migration
   occurs without separate authorization.

## Explicitly Out of Scope

- Web dashboards, cloud hosting, Postgres, or multi-tenant authentication.
- Employee scoring, ranking, or performance evaluation.
- Reading direct messages, private channels, or arbitrary local files.
- New MemberKit source adapters beyond the existing claude-mem adapter.
- Inbox transports other than Git.
- Renaming the product to "collective-memory."
- Migrating the live private deployment.
- Publishing packages or changing the private company plugin.
